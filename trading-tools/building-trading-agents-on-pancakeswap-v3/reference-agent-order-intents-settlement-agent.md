# 参考 Agent — 订单/意图结算 Agent

> 一个 ERC-8183 Provider Agent,每次履行一个兑换意图 Job:通过 PancakeSwap 聚合路由完成兑换,并将目标代币直接交付给 Client。

### 0. 它如何对应 ERC-8183

ERC-8183(Agentic Commerce;Virtuals + 以太坊基金会)定义了一个包含三种角色的 **Job**,其状态为 Open → Funded → Submitted → Terminal。BNB 的 **BNBAgent SDK** 是其在线实现。

| 角色                                                       | 在此 Agent 中                                                                                                                  |
| -------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| **Client**(Agent-A)                                      | 发布兑换意图:"将 X 数量的代币 A 兑换为代币 B,向我交付 ≥ `minOut`",并托管输入资金及小费                           |
| **Provider**(Agent-B)— **这就是我们的参考 Agent** | 通过 **PancakeSwap 聚合**报价,如果能达到或优于 `minOut`,则执行兑换并将代币 B 交付给 Client |
| **Evaluator**                                            | 验证 Client 收到的代币 B 数量 ≥ `minOut`;释放小费(或退还给 Client)                               |

交付成果是客观的("Client 是否收到了 ≥ `minOut`?"),这正是它适合 ERC-8183 而再平衡器不适合的原因。

***

### 1. 目的与一句话范围

> 一个 **Provider** Agent,每次履行一个兑换意图 Job:通过 PancakeSwap 聚合路由完成兑换,并将目标代币直接交付给 Client——仅此而已。

***

### 2. Agent 被允许做什么(能力白名单)

| # | 能力             | 接口                                                     | 说明                                                                      |
| - | ---------------------- | ----------------------------------------------------------- | -------------------------------------------------------------------------- |
| A | 发现开放的 Job     | BNBAgent SDK(ERC-8183 注册表)                            | 只读;筛选出它能服务的兑换意图 Job                         |
| B | 为路由报价         | **PancakeSwap 聚合**(Aggregator API / Smart Router) | 只读;跨 V3 获取最优价格                                            |
| C | 接受 Job           | BNBAgent SDK(Funded → committed)                           | 仅当其最新报价 ≥ `minOut` 且小费 ≥ 下限时                         |
| D | 执行兑换       | PancakeSwap 路由器                                          | 输入资金从 Job 托管中提取;**输出接收方 = Client**,在一笔交易内完成 |
| E | 提交交付成果 | BNBAgent SDK(→ Submitted)                                  | 以结算交易哈希作为证明                                        |
| F | 领取小费          | ERC-8183 托管 / x402                                      | 仅在 Evaluator 将 Job 标记为 Terminal 之后                           |

**每笔结算的输出都直接发送给 Client。Agent 唯一的收入是 Job 的小费。**

***

### 3. 硬性防护措施(入选推荐的门槛)

| 防护措施                              | 规则                                                                                                                                                              |
| -------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **绝不接受无法履行的 Job** | 仅当_最新_报价满足 `minOut` 时才接受 Job。如果做不到,则让该 Job 保持 Funded 状态,留给其他 Provider。                                                     |
| **执行时重新报价**                   | 在结算前立即重新报价;如果路由已无法满足 `minOut`,则中止(不使用过期报价)。                                                             |
| **原子结算**                  | 从托管提取 → 兑换 → 交付给 Client,在**一笔交易**内完成,输出接收方 = Client。Agent 绝不能在某一步失败后仍持有 Client 的资金。 |
| **滑点**                           | 执行滑点须有上限;计入滑点后,交付数量仍必须 ≥ `minOut`,否则交易回滚。绝不使用 `amountOutMin = 0`。                                |
| **截止时间**                       | 结算交易使用较短的截止时间(≤ 5 分钟);同时遵守 Job 自身的截止时间。                                                                                    |
| **最低小费 / 最高价值**                | 不接受小费低于下限或价值高于单个 Job 上限的 Job。                                                                                         |
| **代币安全名单**                     | 仅服务代币位于 PancakeSwap 代币列表中的 Job(防蜜罐 / 假币)。                                                                      |
| **单 Job 并发(v1)**        | 一次只履行一个 Job;不过度承诺。                                                                                                  |
| **Gas 前置条件**                   | 接受 Job 前,确认有足够的 BNB 支付完整结算。                                                                                    |
| **幂等**                         | 绝不重复提交,也不重复履行已处于 Submitted/Terminal 的 Job。                                                               |

如果任何一条规则无法满足,就**跳过该 Job**——绝不强行结算。

***

### 4. 范围之外 — Agent 绝对不得

1. **将 Client 的资金用于指定兑换之外的任何用途。** 输出接收方始终是 Client。
2. **动用自有库存抢先成交 / 承担本金风险。** v1 **仅限从托管提取**——它只路由 Client 托管的输入资金,不会用自己的余额成交。
3. **通过非 PancakeSwap 或未经验证的合约进行路由**,或在 PancakeSwap 聚合之外结算。
4. **服务含非安全名单代币的 Job**,或(v1)任何 scaled-UI / RWA 代币(§5)。
5. **使用杠杆、永续合约、保证金或借贷。**
6. **提交其实际并未履行的交付成果**(不得虚假证明),或**评估自己的 Job**(利益冲突)。
7. **调用** PancakeSwap 或 ERC-8183 合约的**任何 owner/admin 函数**。
8. **持有超出单次结算的长期代币授权**;授权范围限定为 Job 的数量。

***

### 5. PancakeSwap 特定逻辑(应用正确性)

* **通过 PancakeSwap 聚合路由**,而不是单一资金池——跨 V2 / V3 / Stable 的最优执行是全部的价值主张("最优价格赢得小费")。
* **原子交付给 Client**:将路由器的 `recipient` 设为 Client 地址;绝不采用两步式的"先兑换到自己,再转账"。
* **报价新鲜度**——链上价格在发现 Job 与结算之间会变动;在执行时重新报价(防护措施 §3)。
* **`minOut` 以原始单位计。** 对于 **scaled-UI / ERC-8056 代币**(Binance Stock Tokens / RWA 股票),原始数值 ≠ 显示数值;处理不当会悄无声息地造成错误交付。在工程团队确认端到端的原始单位处理之前,**v1 排除 scaled-UI 代币**。
* 结算兑换的**最低滑点**必须这样推导:使_交付_数量 ≥ `minOut`,并计入小费/手续费的分成。

***

### 6. 失败与恢复行为

* **执行时报价不满足 `minOut`** → 在托管提取之前或与之原子地中止;Job 保持 Funded 状态,留给其他 Provider。不留下部分状态。
* **已处于 Submitted/Terminal** → 跳过(幂等)。
* **结算交易回滚** → Job 仍可被其他人领取;Agent 记录失败并继续处理下一个。
* **同一 Job 反复失败** → 在本地将该 Job 列入黑名单并发出警报,而不是循环重试。

***

### 7. 集成点(BNB / ERC-8183 的部分)

这些由 BNB Agent Studio / BNBAgent SDK 提供,并非由 PancakeSwap 构建——但本规范依赖于它们:

* 通过 BNBAgent SDK 实现 **Job 生命周期**(发现 Open → 接受 Funded → Submitted → 领取)。
* 通过 ERC-8004 实现 **Provider 身份**。
* 通过 ERC-8183 托管 / x402 实现**托管与支付**。
* **Evaluator** — 判定条件必须是"Client 的代币 B 余额增加 ≥ `minOut`"。需与 BNB 确认**由谁运行 Evaluator**(中立方/协议方 vs. Client),以及该判定条件能否在链上强制执行。

***

### 8. 建议的 v1 立场与待定事项

1. **仅限从托管提取、一次一个 Job、仅限代币安全名单、不含 scaled-UI 代币。** 这是上线时推荐的最小安全范围。
2. **确认 PancakeSwap 兑换接口** — **Aggregator(`aggr`)HTTP API** 还是 **Smart Router SDK**。Jerry 的备注写的是"use pcs aggr api";需要确认 Agent 具体调用哪一个,因为这会改变集成方式(以及指南是否需要增加聚合部分)。
3. **与 BNB 确认托管机制** — Provider 能否提取 Client 托管的输入资金来路由兑换,以及"交付给 Client"能否作为交付成果被强制执行?
4. **确认 Evaluator 的所有者和判定条件**(§7)。

> 推荐前需工程团队签字确认:原子化的托管提取 → 兑换 → 交付给 Client 路由;执行时重新报价;计入滑点后的 `minOut` 计算;安全名单强制执行;幂等的 Job 处理。
